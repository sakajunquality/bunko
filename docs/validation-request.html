Bunko application validation
v0.1.0-rc.2

Please re-test the application from the original compatibility report on its own machine. Use an isolated checkout and disposable services. The goal is functional parity for the web server, worker, bot and explicit migration job, including real runtime files and native behavior.

Release candidate, not workload certification. Use the immutable rc.2 release after its assets are available. If the release is not yet published, wait for it; do not substitute rc.1 or alpha.2. Record the CLI checksum and release commit. Application results below remain unverified until you execute them.

1. What changed since the original report

RequestCandidate behavior / remaining adaptation
R1Restricted install-only bunfig settings are supported. Only minimumReleaseAge and minimumReleaseAgeExcludes are forwarded; test settings are ignored. Other unsupported keys still fail.
R2–R3Executable checks follow loaded bundle inputs. Copy-only frontend assets and unreachable dependencies are not scanned as executable code. Real macros remain rejected before execution. Relative JSON/text/file/TOML data imports are supported.
R4–R5Explicit unresolved dependency allowances and allowIgnoredScripts are available. Hooks never run. Recognized foreign native variants and their aliases are pruned; corrupt or unknown addons still fail. You must prove required dynamic packages and target native binaries are present and functional.
R6Named entries share an image with a default command. Use emitted paths from the build report to select worker, bot or migrate.
R7Named local asset contexts map selected files to absolute image destinations such as /repo. All bindings are explicit.
R8Source-preserving mode remains unimplemented. Optional runtime.inject: release adds verified Bun to an explicit glibc base; gpgv is required on the build host and native shared libraries must still come from the base. Prepared Bun-containing bases remain supported.
R9inheritBaseOciLabels: false suppresses inherited OCI labels. It does not anonymize source, package names or reports.

2. Pin tools and isolate output

Use Bun 1.3.11, 1.3.12 or 1.3.13; Bun 1.4 is outside this candidate's range. Docker must support the architecture being tested. Use native machines where possible and record emulation when used. Download bunko.js, SHA256SUMS, LICENSE and THIRD_PARTY_NOTICES.md from the same rc.2 release into a private tool directory.

  • Native dependencies: externalize location-sensitive packages as needed, based on the resolved inventory. The example allowances are candidates from the original report, not a blanket approved list. Confirm published files work without hooks. If the original opaque dependency expressions still require runtime resolution, explicitly add "build": { "allowUnresolved": [""] } after auditing those imports. Prefer exact specifier patterns for identifiable imports; the empty pattern allows opaque expressions broadly and does not install missing runtime packages.
  • Runtime files: create a local manifest of source path → image path → expected content/hash. Adapt import.meta-relative reads to declared image paths or embed explicit data imports. Review BUNKO_MODULE_LOCATION warnings and use an explicit runtime root where bundling relocates a module. Confirm exact file content; a warning followed by a default value fails acceptance.
  • Temporal: prebuild workflows with bundleWorkflowCode in the trusted preparation step. Configure the worker with workflowBundle.codePath to the copied bundle instead of runtime workflowsPath compilation. See the official production worker example. Verify the native bridge and required shared libraries on each architecture.
  • Migrations: provide one explicit entry that calls the migration API and every ordered synchronization step. Shell command chains and external CLI executables are not automatically bundled. A separate trusted migration preparation job is an acceptable operational fallback, but then mark the migration-image criterion not-run.
  • Base: digest-pin a base already containing the selected Bun runtime and native libraries, including libgcc where required. Alternatively enable runtime.inject: release with a compatible glibc base and pass --runtime-inject release to check-base. See the injection guide. A generic check-base pass is insufficient proof for Temporal or Snowflake.

4. Diagnose, build and load locally

bun "$BUNKO_CLI" check-config "$APP_COPY" \
  --asset-context "generated=$GENERATED_INPUTS" \
  > "$BUNKO_QUARANTINE/config.json" 2> "$BUNKO_QUARANTINE/config.log"
bun "$BUNKO_CLI" doctor "$APP_COPY" \
  --asset-context "generated=$GENERATED_INPUTS" \
  > "$BUNKO_QUARANTINE/doctor.json" 2> "$BUNKO_QUARANTINE/doctor.log"
# With runtime.inject: release in configuration, add --runtime-inject release to check-base.
bun "$BUNKO_CLI" check-base --base "$BASE" --platform "$PLATFORM" --run \
  > "$BUNKO_QUARANTINE/base.json" 2> "$BUNKO_QUARANTINE/base.log"

# For a workspace, invoke at the root and add --target with the server member.
# Use fresh output paths for each architecture.
bun "$BUNKO_CLI" build "$APP_COPY" \
  --base "$BASE" --platform "$PLATFORM" \
  --asset-context "generated=$GENERATED_INPUTS" \
  --push=false --git-metadata=false --no-cache \
  --install-cache "$BUNKO_QUARANTINE/install-cache" \
  --repo bunko.local/validation-app --bare --tag candidate \
  --oci-layout "$BUNKO_QUARANTINE/layout" \
  --tarball "$BUNKO_QUARANTINE/image.tar" \
  --report "$BUNKO_QUARANTINE/build.json" \
  > "$BUNKO_QUARANTINE/build.stdout" 2> "$BUNKO_QUARANTINE/build.log"
docker load --input "$BUNKO_QUARANTINE/image.tar" \
  > "$BUNKO_QUARANTINE/load.log" 2>&1

5. Required acceptance matrix

Record pass, fail or not-run for each architecture separately. Run the current deployment image against the same disposable data as a baseline when behavior is ambiguous.

IDRequired evidence
A01Unpatched rc.2 configuration and build succeed. Record public CLI checksum, Bun revision, target architecture, emulation and base digest.
A02SPA shell, hashed JS/CSS and public assets match generated content; a deep-link route loads and the browser hydrates without console errors.
A03Database health succeeds with a real connection; a representative API transaction reads/writes expected data. A connection-refused response is not a pass.
A04Every YAML/Markdown/generated file is read from the expected image location with expected content. No default prompt, empty config or fallback warning.
A05Migration plus every synchronization step changes the disposable schema/data as expected. Repeat according to the application's idempotency contract. No server-start migration side effect.
A06Actual Temporal worker connects and completes a workflow/activity with expected result using the prebuilt bundle. Verify native bridge load; startup alone is insufficient.
A07Bot handles one test event and produces the expected response in a designated test destination. No production messages.
A08Snowflake native/minicore path is active and completes a representative test query/auth flow. Missing-binary or fallback-only behavior fails this criterion.
A09Default server and overridden worker/bot/migrate commands use the same image and the reported emitted paths. Confirm effective UID is non-root and root filesystem is read-only.
A10SIGTERM stops each long-running role within the deployment grace period, drains work as designed and exits without SIGKILL/OOM. Record the expected exit behavior.
A11Image configuration has the intended labels and no unintended base OCI labels. Confirm publication is disabled and all raw outputs remain private.
