# Performance and cache correctness

`--jobs 1` is the default. Set `--jobs 2` (or `BUNKO_JOBS=2`) to prepare workspace targets concurrently. The limit is 32. Output order stays in target order. All started tasks finish before cleanup; no image is published until every target has prepared successfully. Targets publish one after another.

## Publication concurrency

A warm push is dominated by round trips, not bytes: every layer costs a HEAD even when the registry already has it, and a distant registry answers in roughly 100-150 ms. The blobs of one manifest — its layers and its config — are therefore placed in parallel, bounded by `--publish-concurrency` (or `BUNKO_PUBLISH_CONCURRENCY`), 1-32, default 6 and 3 for Docker Hub. Ordering is unchanged: a manifest is written only after every one of its blobs is present, one platform manifest completes before the next one starts, and the index follows all of them. Reported transfers keep manifest order whatever order the registry answers in, so reports and digests are unaffected by the bound.

A failed placement stops new work, waits for the work already started, and reports the first failure in manifest order; the blobs that did land are still reported, so no upload is left in flight or unrecorded. Registry cache artifacts (`bunko-cache-v1-*`) publish under the same bound, one artifact per slot, each placing its own config and layer serially so the two bounds cannot multiply. A burst also shares one token exchange per scope instead of one per blob, and a 429/503 pauses the registry client for the `Retry-After` it asked for — on reads and on upload recovery alike — so workers that meet the limit during that pause wait it out together. Raise the bound for a distant registry on a well-connected runner; lower it when a registry meters requests per account (see [REGISTRIES.md](REGISTRIES.md)).

The `publication` section of `--report` carries `elapsedMs` and the `blobs` counts (`reused`, `mounted`, `uploaded`, `wouldUpload`) for the whole phase, and the final build log line repeats them. Elapsed time includes each attached SBOM/provenance artifact's complete attachment — referrers probing, verification retries and any fallback index write — not only the blobs and manifest it places; external signing is not measured.

Application layers are cached by default. `--no-app-cache` disables only this cache; `--no-cache` disables every persistent layer cache. Keys include the complete source snapshot, normalized dependency inputs, executable bytes and revision, host/target platform, base digest, build settings, runtime dependency layers, aliases, packing format and timestamp. Workspace source changes conservatively invalidate every application key. A hit skips the build-only dependency installation and bundling; runtime dependencies and source validation still run. `--verify-deterministic` bypasses all layer caches and independently builds twice.

In a workspace, the host build dependency install is scoped to the selected target and the workspace root (§3 of the [specification](SPEC.md)), so a large unrelated member no longer costs every build that misses the application cache. It is reported as its own `build-deps` stage in `timings` and OpenTelemetry, nested inside `assemble`, where it was previously invisible. A target that imports a sibling member's source directly needs that sibling's dependencies too; the build detects an unresolved import or a successful bundle reading a member outside the guaranteed filtered scope, logs `Build dependencies: falling back to a full workspace install (…)`, reinstalls the whole workspace into the same staging root and bundles once more, which produces byte-identical output. Bunko does not cache the installed host tree between builds; the measurements below record why that was not pursued for the workspace shape that was measured.

Successful syntax validation is memoized within one invocation, with a bounded 50,000-entry cache. Every lookup rereads and hashes the bytes, and the parser filename is part of the key. Failed validation is never memoized. This avoids repeated parsing across workspace targets and platforms, while a cold scan still inspects installed JavaScript/TypeScript. The `syntaxValidation` report counters are invocation-wide snapshots, not per-target costs to sum.

With `deps.strategy: closure`, a plan key computed before installation indexes the content-addressed closure key. On a hit whose closure layer is still available, the build skips the frozen Linux production install and the per-file projection of the installed tree, and replays the recorded inventory, native metadata, target aliases, package sizes and dependency paths, and undeclared/optional-import findings under the selected policy; it logs `Reusing dependency closure (<architecture>)`. The plan key omits the selected targets' own workspace source bytes, because a target's own files ship in the application layer rather than the closure, so editing the target's sources no longer invalidates the closure in a workspace whose other members depend on the target; a projection that does contain a selected target (a dependency cycle, a self-referencing external, or one shared target externalising another) records no plan and reuses none, and installs and projects as before. Lock validation, base validation, source snapshotting and the application cache are unaffected, and a miss falls back to installing and projecting. A prepared plan also lets `--offline` reuse a closure that an online build recorded. Plans live in `plans/deps` under the local cache directory, are counted by `cache-info`, and are reclaimed by `prune` together with the key record they name.

Plans are also published to the registry cache, as `bunko-cache-v1-deps-plan-*` artifacts alongside the layer artifacts. A fresh CI runner therefore needs only the cache repository for the warm path: on a local miss the plan is read from the ordered `--cache-from` sources and the cache repository, the closure layer it names comes from the registry too, and the build skips the frozen Linux install and the projection on its first run — where it previously re-ran both and only then discovered that the layer already existed. The registry plan is written through to the local cache once that layer is durable there, so the next build on the same runner never leaves the machine. This makes a restored `cache-dir` an optimization rather than a requirement for closure reuse; a CI cache service is still worth using for Bun's package download cache (`install-cache`). The managed local cache directory must still be enabled: `--no-local-cache` and `--no-cache` consult no plan from any transport, because they exist to force a clean local flow and leave no index for a hit to be written through to. Every closure build also records one `deps-plan` lookup entry in the report's `cache` array, local-only builds included; it describes the closure index rather than a layer, so exclude it when aggregating layer reuse.

## Base inspection

Every build inspects the base filesystem before it can validate the workdir, place the runtime and derive the static CA/font/shell/user/shared-library evidence: each base layer is decompressed, its DiffID rehashed, written to build staging and scanned as a tar stream, and the merged tree of paths, types, modes, sizes and link targets is kept in memory. The base is addressed by an immutable digest, so that tree is a pure function of (base digest, inspection logic), and it is now stored as one JSON record under `base-inspect/<inspection-version>` in the local cache directory and replayed on the next build. The record is validated on read against the inspection version, the requested digest and the entry shape inspection could have produced; anything else is a miss and the base is inspected again. A hit logs `Reusing inspected base filesystem (<digest>)` and adds a `base` entry to the report's `cache[]`; the `base-inspect` phase stays in `timings` and simply becomes short.

Because the record replaces the decode, a hit also leaves the base layer blobs deferred: they are pulled only when assembly or publication actually needs them, and a push that cross-repo mounts them may never pull them at all. Verification follows materialization rather than inspection — an OCI layout export checks compressed digests and sizes, a Docker archive export (`--tarball`, `--local`, `--kind`) still decodes every layer and verifies its DiffID, and a mounted blob is never read. The tree is metadata, so nothing about image identity depends on it being cached — a warm build produces the same config, layers and digests as a cold one. `--no-cache` and `--no-local-cache` neither consult nor write the record. `--verify-deterministic` does consult it, because the base is pinned for the whole build and one inspection is shared by both iterations, so neither iteration can observe a different base. Records live beside closure plans in the managed cache: they own no blobs, are counted by `cache-info`, and are ordinary oldest-first `prune` candidates, since losing one only costs the next build another inspection.

Local writers and prune cooperate through a directory lock. A valid, different layer under the same key causes a conflict instead of being overwritten. Readers verify copied blobs and tolerate missing/corrupt entries as misses. A stale lock is not automatically broken; inspect its owner before removing it. Remote cache publication checks existing records and refuses conflicting output. Registry tag updates do not provide universal compare-and-swap, so this is not a distributed transaction guarantee. Use a trusted cache repository: content addressing detects corruption, not a malicious writer replacing an entire valid record.

## Measurements

Run `bun run bench:performance` from an installed checkout. The benchmark prints its runtime, host, input count, timings, counters and resulting digests. It does not run as a unit test.

One macOS arm64 / Bun 1.4.2 run built a 189-package closure fixture against a local base layout, alternating warm builds between releases under concurrent load. Without the plan key each warm build spent 0.88-1.15 s in the Linux install and 7.4-10.2 s in assemble; with it the install phase disappeared and assemble took 0.24-0.46 s, for the same deps layer digest, inventory and diagnostics. On `examples/workspace` and `examples/dependencies` the same fixtures are small enough that the saving is tens of milliseconds. These are illustrative single-host measurements, not a general speedup claim.

One macOS arm64 / Bun 1.4.2 run measured the push phase against an in-memory Distribution endpoint with 100 ms of simulated latency per request, publishing a manifest whose 18 base/dependency/asset layers already existed and whose application layer and config were new. The sequential implementation took 3,236 ms; the bounded-parallel one took 1,218 ms at the default 6, 1,528 ms at 3, 1,130 ms at 8 and 1,023 ms at 12. Both issued the same 32 requests and reported the same 20 transfers in the same order. Simulated latency is not a substitute for a live registry, and a real push also pays for bytes.

One macOS arm64 / Bun 1.4.2 run measured the host build dependency install on a 778-package workspace whose unrelated member pulls Expo and React Native, with a warm download cache and a target using 15 packages. The unscoped install took 4.0-4.6 s per build and the `--filter` scoped install 0.65 s; the same shape on `examples/workspace` with that member added went from 3.95-3.99 s to 35-76 ms, and Bun 1.3.13 from 3.2-5.3 s to 0.62-0.81 s. Reusing a stored copy of the *unscoped* tree instead was measured on that fixture and not pursued: restoring its 763-package `node_modules` (296 MB, 28,081 entries) took 35.1 s with a link-preserving `fs.cp`, 18.7 s with `cp -R`, 15.3 s with `cp -Rl` hardlinks and 7.4 s with `cp -Rc` APFS clones, against a 4.6 s reinstall from the warm download cache. The scoped 15-package tree was not measured, so no conclusion is drawn about caching it. These are illustrative single-host measurements on one filesystem, not a general speedup claim, and the fixture is not committed.

One macOS arm64 / Bun 1.4.2 run measured base inspection of `oven/bun:1.4.2-distroless` (linux/amd64: 16 layers, 41.3 MiB compressed, 91.6 MiB uncompressed, 1,684 entries) on a residential connection, with every other cache warm in both directions. The `base-inspect` phase took 6,190/6,656/6,425 ms without a record and 4/6/5 ms with one; the whole build went from 10.1-10.4 s to 3.8-4.0 s, for identical index, manifest, config and layer digests. Against a warm blob store the phase splits into 3.24 s of registry layer pulls, 1.42 s of `decodeLayer` (gunzip, DiffID rehash and write of 91.6 MiB) and 0.02-0.30 s of tar scanning, so a record removes the decode always and the pulls whenever nothing else materializes those blobs. The record itself is 150 KB of JSON and parses back in 0.6 ms. The same run on a 2,001-entry local base layout — no network at all — went from 143-251 ms to 1.7-2.9 ms. These are illustrative single-host measurements, not a general speedup claim; a CI runner with a fast registry path pays less for the pulls and correspondingly more of the saving comes from the decode.

One macOS arm64 / Bun 1.3.11 run scanned 504 installed files. The first memoized pass took 1,553 ms and the second 125 ms, including rereading/hashing the same bytes. A small dependency fixture built in 338 ms cold and 179 ms with local caches, with identical image digests. These are illustrative measurements under concurrent test load, with filesystem warming and fixed execution order; they are not a general speedup claim. Raw output is in `validation/performance.json`.

## Comparing image sizes

The final log reports stored layer bytes per platform, including base layers, and the base/deps/assets/app/runtime breakdown. Units are decimal MB. The compression label reflects the actual media types; mixed or uncompressed bases are not described as fully compressed. These are descriptor totals, not push traffic or registry billing, and platforms are reported separately because they may share blobs. Docker archive export and local loading expand layers. Do not compare a local Docker size with a registry layer total as though both measured the same thing.
