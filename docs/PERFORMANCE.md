# Performance and cache correctness

`--jobs 1` is the default. Set `--jobs 2` (or `BUNKO_JOBS=2`) to prepare workspace targets concurrently. The limit is 32. Output order stays in target order. All started tasks finish before cleanup; no image is published until every target has prepared successfully. Publication stays sequential.

Application layers are cached by default. `--no-app-cache` disables only this cache; `--no-cache` disables every persistent layer cache. Keys include the complete source snapshot, normalized dependency inputs, executable bytes and revision, host/target platform, base digest, build settings, runtime dependency layers, aliases, packing format and timestamp. Workspace source changes conservatively invalidate every application key. A hit skips the build-only dependency installation and bundling; runtime dependencies and source validation still run. `--verify-deterministic` bypasses all layer caches and independently builds twice.

In a workspace, the host build dependency install is scoped to the selected target and the workspace root (§3 of the [specification](SPEC.md)), so a large unrelated member no longer costs every build that misses the application cache. It is reported as its own `build-deps` stage in `timings` and OpenTelemetry, nested inside `assemble`, where it was previously invisible. A target that imports a sibling member's source directly needs that sibling's dependencies too; the build recognizes the resulting unresolved-import failure, logs `Build dependencies: falling back to a full workspace install (…)`, reinstalls the whole workspace into the same staging root and bundles once more, which produces byte-identical output. Bunko does not cache the installed host tree between builds; the measurements below record why that was not pursued for the workspace shape that was measured.

Successful syntax validation is memoized within one invocation, with a bounded 50,000-entry cache. Every lookup rereads and hashes the bytes, and the parser filename is part of the key. Failed validation is never memoized. This avoids repeated parsing across workspace targets and platforms, while a cold scan still inspects installed JavaScript/TypeScript. The `syntaxValidation` report counters are invocation-wide snapshots, not per-target costs to sum.

With `deps.strategy: closure`, a plan key computed before installation indexes the content-addressed closure key. On a hit whose closure layer is still available, the build skips the frozen Linux production install and the per-file projection of the installed tree, and replays the recorded inventory, native metadata, target aliases, package sizes and dependency paths, and undeclared/optional-import findings under the selected policy; it logs `Reusing dependency closure (<architecture>)`. The plan key omits the selected targets' own workspace source bytes, because a target's own files ship in the application layer rather than the closure, so editing the target's sources no longer invalidates the closure in a workspace whose other members depend on the target; a projection that does contain a selected target (a dependency cycle, a self-referencing external, or one shared target externalising another) records no plan and reuses none, and installs and projects as before. Lock validation, base validation, source snapshotting and the application cache are unaffected, and a miss falls back to installing and projecting. A prepared plan also lets `--offline` reuse a closure that an online build recorded. Plans live in `plans/deps` under the local cache directory, are counted by `cache-info`, and are reclaimed by `prune` together with the key record they name.

Local writers and prune cooperate through a directory lock. A valid, different layer under the same key causes a conflict instead of being overwritten. Readers verify copied blobs and tolerate missing/corrupt entries as misses. A stale lock is not automatically broken; inspect its owner before removing it. Remote cache publication checks existing records and refuses conflicting output. Registry tag updates do not provide universal compare-and-swap, so this is not a distributed transaction guarantee. Use a trusted cache repository: content addressing detects corruption, not a malicious writer replacing an entire valid record.

## Measurements

Run `bun run bench:performance` from an installed checkout. The benchmark prints its runtime, host, input count, timings, counters and resulting digests. It does not run as a unit test.

One macOS arm64 / Bun 1.4.2 run built a 189-package closure fixture against a local base layout, alternating warm builds between releases under concurrent load. Without the plan key each warm build spent 0.88-1.15 s in the Linux install and 7.4-10.2 s in assemble; with it the install phase disappeared and assemble took 0.24-0.46 s, for the same deps layer digest, inventory and diagnostics. On `examples/workspace` and `examples/dependencies` the same fixtures are small enough that the saving is tens of milliseconds. These are illustrative single-host measurements, not a general speedup claim.

One macOS arm64 / Bun 1.4.2 run measured the host build dependency install on a 778-package workspace whose unrelated member pulls Expo and React Native, with a warm download cache and a target using 15 packages. The unscoped install took 4.0-4.6 s per build and the `--filter` scoped install 0.65 s; the same shape on `examples/workspace` with that member added went from 3.95-3.99 s to 35-76 ms, and Bun 1.3.13 from 3.2-5.3 s to 0.62-0.81 s. Reusing a stored copy of the *unscoped* tree instead was measured on that fixture and not pursued: restoring its 763-package `node_modules` (296 MB, 28,081 entries) took 35.1 s with a link-preserving `fs.cp`, 18.7 s with `cp -R`, 15.3 s with `cp -Rl` hardlinks and 7.4 s with `cp -Rc` APFS clones, against a 4.6 s reinstall from the warm download cache. The scoped 15-package tree was not measured, so no conclusion is drawn about caching it. These are illustrative single-host measurements on one filesystem, not a general speedup claim, and the fixture is not committed.

One macOS arm64 / Bun 1.3.11 run scanned 504 installed files. The first memoized pass took 1,553 ms and the second 125 ms, including rereading/hashing the same bytes. A small dependency fixture built in 338 ms cold and 179 ms with local caches, with identical image digests. These are illustrative measurements under concurrent test load, with filesystem warming and fixed execution order; they are not a general speedup claim. Raw output is in `validation/performance.json`.
